## Decision Made: Emission Engine for Go Source

**Chosen: `dave/jennifer` (`github.com/dave/jennifer/jen` v1.7.1).**
**Hybrid: continue using `text/template` for non-Go artifacts (SQL DDL, Markdown, Makefile fragments) per `STACK.md`.**

### Criterion-by-criterion evidence

The four criteria are verbatim from `00-CONTEXT.md` `<decisions>` "Emission-engine spike". Quantitative observations come from the actual spike code committed in this plan.

1. **Import management (Win: Jennifer).**
   - `spike/template/user.go.tmpl` carries **8 conditional-import guard lines** (`{{- if .HasX }}…{{- end }}`) routing imports for `time`, `regexp`, `slices`, `fmt`. Every new IR feature with a new import adds another guard.
   - `spike/jennifer/main.go` has **0 such guards** and **7 `jen.Qual` call sites** covering the same 4 packages — Jennifer's emitter walks the AST and produces the import block automatically. New imports are one more `Qual` at the call site, no bookkeeping.

2. **Source readability (Win: text/template).**
   - `spike/template/user.go.tmpl` is **67 LOC**; the runner glue is **65 LOC**. The template reads as the Go file we want, with `{{ }}` toggles where the IR varies — a contributor unfamiliar with the codebase can scan it instantly.
   - `spike/jennifer/main.go` is **117 LOC** of method-chain prose (`jen.Id("ID").String().Tag(...)`); reading it requires familiarity with Jennifer's API to translate chain calls back to Go source.

3. **Diff stability (Tie).**
   - Both engines produce gofmt-clean output (verified by `gofmt -l` returning empty for both).
   - `spike/run.sh` runs each engine twice consecutively and asserts byte-identical output across runs — both pass. REQ-GEN-06 dry run is satisfied for both.

4. **Mixed-output compatibility (Neutral / hybrid).**
   - Jennifer is Go-only by design; `text/template` covers all our other emission targets. Picking Jennifer for Go does not preclude using `text/template` for non-Go artifacts — they coexist in the same `gen/internal/emit/` once Phase 2 starts.

### Why the import-management win trumps the readability loss

The IR will carry many more conditional imports as the schema surface grows in Phase 1+ (datetime, binary, reference, complex sub-attributes, each with their own validators). Manual import bookkeeping in templates compounds linearly with feature count and is a documented foot-gun (`00-RESEARCH.md` "Don't Hand-Roll" cites hand-rolled import tracking as the second-most-cited cause of "regen produces noisy diff" in the Go codegen ecosystem). The readability cost is contained to one module in `gen/`; the import-management cost in templates would compound across every emitter we add. We chose the structural win over the local readability win.

### Tradeoffs accepted

- Jennifer's call sites are wordier than template equivalents.
- One additional third-party dep in `gen/` (Jennifer v1.7.1, MIT, "stability-stable", Sept 2024). Slow update cadence is acceptable for a build-tool dep.
- Two engines coexist in the generator (Jennifer for Go, `text/template` for SQL/Markdown/Makefile). This is the design, not a leak.

### Fallback option (documented for Phase 2)

If Jennifer's API ergonomics turn out worse than expected, the documented compromise is `text/template` + `golang.org/x/tools/imports.Process` (the library form of `goimports`, which adds and removes imports based on the rendered Go source). Signals that would trigger the swap: emitter modules in `gen/internal/emit/` exceeding ~400 LOC of method-chain prose for a single artifact, or new contributors repeatedly bouncing off "I can't tell what this Jennifer code emits without running it." See `00-RESEARCH.md` Open Question 1 for the prototype path.

`imports.Process` was **documented as the fallback only — not prototyped in this plan**. Adding a third spike leg would have been scope creep against the CONTEXT.md-frozen contract.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Jennifer `If(...)` with multiple expressions emitted `;` instead of `&&`**

- **Found during:** Task 2 (initial `go run .` panicked in `format.Source` with "expected operand, found '&&'" because Jennifer joined two args to `If(...)` with a semicolon)
- **Issue:** I initially wrote the canonicalValues check as `jen.If(jen.Id("u").Dot("Title").Op("!=").Lit(""), jen.Op("&&").Op("!").Qual(...))`. Jennifer's `If(...)` variadic separates statements with `;` (it's the init-statement form), not boolean composition.
- **Fix:** Composed the two predicates into a single chained expression with `.Op("&&")` joining them, so Jennifer emits one boolean expression.
- **Files modified:** `spike/jennifer/main.go`
- **Verification:** `GOWORK=off go run .` succeeds; `gofmt -l` clean; cross-engine diff passes.
- **Committed in:** `be17500` (Task 2 commit)

**2. [Rule 1 - Bug] spike/template output didn't match canonical form (UserEmail order, regex literal style)**

- **Found during:** Task 2 (after running both engines, the `diff -I '^// Code generated'` showed three substantive differences)
- **Issue:** Templates emitted `User` before `UserEmail` and used a backtick raw-string regex literal; Jennifer emitted `UserEmail` before `User` and used a double-quoted regex literal. The plan demands byte-equivalent output modulo header (verification step #3).
- **Fix:** Updated `spike/template/user.go.tmpl` to emit `UserEmail` before `User` and use a double-quoted regex literal (the regex pattern contains no double-quote chars or escapes, so the literal form is interchangeable). Re-ran the template runner.
- **Files modified:** `spike/template/user.go.tmpl`, `spike/template/output/user_gen.go`
- **Verification:** `diff -I '^// Code generated' spike/template/output/user_gen.go spike/jennifer/output/user_gen.go` returns empty.
- **Committed in:** `be17500` (Task 2 commit, bundled with the Jennifer module)
