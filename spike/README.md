# Emission-engine spike

## Why this exists

`STACK.md` and `ARCHITECTURE.md` disagree explicitly on the engine the
generator should use for Go-source emission (`text/template` + `go/format`
vs. `dave/jennifer`). The argument cannot be settled by personal preference;
it must be settled on observed evidence against the four scoring criteria
listed below. This directory holds both candidate implementations
permanently as the audit trail. When a future contributor proposes
re-litigating the choice, they point here.

## The artifact contract (frozen)

Both engines produce the same Go file: a typed `User` struct + nested
`UserEmail` + a `Validate()` method. The artifact deliberately exercises the
three places where the two engines diverge in practice:

1. **Conditional imports** — `time` (datetime field), `regexp` (pattern
   constraint), `slices` (canonicalValues check), `fmt` (error returns).
2. **Nested types** — `Emails []UserEmail` where `UserEmail` is its own struct.
3. **Branching validation** — required check, regex pattern check,
   canonicalValues check via `slices.Contains`, multi-valued primary
   cardinality check.

The fixture data in each runner's `userData` struct toggles every
conditional path on so the gnarly emission path is exercised.

## How to run

Each spike is a standalone Go module excluded from the main `go.work` (per
`CONTEXT.md`).

```bash
# Run a single engine:
cd spike/template && GOWORK=off go run .
cd spike/jennifer && GOWORK=off go run .

# Run both, diff their outputs, prove deterministic regen:
./spike/run.sh
```

`spike/run.sh` runs each engine twice consecutively and asserts byte-identical
output across runs (REQ-GEN-06 dry run), then diffs the two engines' outputs
against each other ignoring the engine-attribution header line.

## Scoring criteria (from `CONTEXT.md`)

1. **Import management** — does the engine auto-track imports across
   conditional emission paths?
2. **Source readability** — can a contributor reading the emitter understand
   what it produces?
3. **Diff stability** — two regen runs produce byte-identical Go (REQ-GEN-06
   dry run).
4. **Mixed-output compatibility** — Go-emission winner does not preclude
   using `text/template` for non-Go artifacts (SQL/Makefile/README) per
   `STACK.md`.

## Decision

The decision and per-criterion evidence are recorded in the project's single
source of truth: **`PROJECT.md` → `## Key Decisions` → "Emission engine for
Go source"**. This directory is the citation, not the verdict.

## Header normalisation

Each engine emits its own attribution header (`// Code generated by
spike/template. DO NOT EDIT.` vs `// Code generated by spike/jennifer. DO
NOT EDIT.`). The engine name is informative when reading either file in
isolation; `spike/run.sh` ignores that single line via `diff -I '^// Code
generated'` so the byte-comparison reflects only the substantive content
(struct shape, imports, Validate body).

## Why both implementations stay in-repo

Per the catastrophic-failure mode documented in `00-RESEARCH.md` (Pitfall 1
"Spike concludes before evidence is captured"), the loser is **not deleted**.
A future contributor who second-guesses the engine choice points here, runs
`./spike/run.sh`, reads both `main.go` files side by side, and weighs the
same evidence we did. The comparison stays cheap to re-evaluate.

## Phase 2 fallback: `text/template` + `imports.Process`

If the chosen engine's drawbacks become painful in Phase 2, the documented
compromise is `text/template` + `golang.org/x/tools/imports.Process` (the
library form of `goimports`). This combines templates' readability with
automatic import management. The spike does not build this third leg —
adding it would be scope creep — but `imports.Process` is the natural escape
hatch noted in `00-RESEARCH.md` Open Question 1.

## Scope freeze

If you are tempted to add features to either spike (a JSON marshaller, an
SQL repo emitter, etc.), those features belong in Phase 2's
`gen/internal/emit/` — not here. The spike artifact is frozen at the
contract above (`00-RESEARCH.md` Pitfall 6: "Spike scope creep into 'real'
generator code").
